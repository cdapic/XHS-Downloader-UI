## 一、结论先行（TL;DR）

**一句话定位**

> 从「小红书单篇下载工具」走向「自托管的个人内容素材库」——以 **采集 → 归档 → 检索 → 复用** 四步闭环为主线，把"用完即走"的下载行为沉淀为可反复使用的个人内容资产。

**推荐主线（四方向中选一个）**

推荐 **方向 B：资产型（个人内容素材库）**，并以 **方向 A（加固）作为不可跳过的前置盘**、**方向 C（创作工作台）作为其自然延伸**、**方向 D（多平台化）明确本期不做**。

**三个版本的节奏**

| 版本 | 主题 | 解决什么 | 定位 |
|---|---|---|---|
| **v1.1** | 内网可用 + 健壮性 | 白板故障、卡死不可取消、错误黑盒 | 地基加固，**必做前置** |
| **v1.2** | 批量采集 | 一条一条粘贴的低效 | 效率台阶，**建立"批量"心智** |
| **v2.0** | 素材库 | 下载完就找不到、无法检索复用 | **价值分水岭，从工具变产品** |

**三条不可越的红线**

1. **合规红线**：坚持个人非商业备份定位。不做自动化登录、不做账号级批量抓取、不做风控绕过、不做多平台聚合抓取。
2. **架构红线**：不引入 Redux/RTK Query；后端跟上游不 fork；nginx 同源反代与 5556 端口绑定现状不擅自改动（沿用 `memory-bank/activeContext.md` 决策 1/2/3/5/7）。
3. **不推倒重来**：现有单篇解析链路、同源部署方案、`services/components/hooks/utils` 分层、i18n 双语言机制均已被验证可行，增量演进而非重构。

### 2.3 已经做对、不要动的部分

- **同源反代架构**（浏览器只看 nginx，`getDefaultApiUrl()` 返回 `window.location.origin/xhs/detail`）——优雅，避免了 CORS 与后端端口暴露到前端配置里。
- **后端不 fork、跟上游**——上游已修复的问题不重复造轮子，已用 79 个 commit 的合并验证过。
- **分层清晰**（`services` / `components` / `hooks` / `utils` / `constants` / `types`）——规模小但不乱，无需引入状态库。
- **降级意识已存在**（剪贴板 execCommand 降级、localStorage 读写 try-catch 静默降级、视频 fetch 失败给 Open Original 出口）——这是好底子，值得在 v1.1 继续沿这个风格扩展。

## 三、问题诊断（分级摘要）

## 四、方向选择

### 4.1 先看清这个产品站在价值链的哪一格

内容创作者的工作流是：

```
发现好内容 → 【素材采集】 → 素材沉淀 → 素材整理/检索 → 创作产出 → 发布 → 复盘
                  ▲
             本项目当前只占这一格
```

当前产品**只解决了"搬下来"**，没有解决"搬下来之后怎么办"。用户下载完一个 ZIP，文件进硬盘某个角落，下次要找同类素材时只能**重新去小红书翻一遍**——这是最大的价值漏损点。

### 4.2 四个候选方向

#### 方向 A：加固型 ——「稳定可靠的自托管下载器」

- **内涵**：不扩功能品类，把现有单篇链路的可靠性做到工业级：内网可用、错误可诊断、可取消、可校验、有测试、可观测。
- **价值**：解决 IS-01/02/03/05/06/15 这批真实痛点。
- **成本**：低（约 1 个迭代）。
- **风险**：低。
- **天花板**：明显。它不产生任何新的用户价值维度，做完之后用户依然面对"下载完找不到"的问题。

#### 方向 B：资产型 ——「个人内容素材库」★ 推荐主线

- **内涵**：从"一次性下载"升级为"**可沉淀、可检索、可复用**的素材资产库"。批量解析 → 自动归档 → 本地索引 → 标签/检索 → 去重与增量。
- **价值**：
  1. 把用户的重复劳动变成一次性资产（找过的素材不用再找一遍）；
  2. 建立"用户会回来"的理由——**这是从工具变成产品的分水岭**（工具用完即走，产品有留存）；
  3. 与项目「个人备份」的合规定位**完全一致**，不越任何红线。
- **成本**：中。需要把存储从 localStorage 迁到 IndexedDB（突破 5MB / 50 条上限）、设计去重键（作品ID）、缩略图缓存策略、检索索引。
- **风险**：中（浏览器存储配额与驱逐、大数据量下的索引性能）。
- **为什么是它**：投入产出比最高，且是后续一切价值增益（含创作辅助）的**数据地基**。

#### 方向 C：工作台型 ——「创作者素材工作台」

- **内涵**：在素材库之上做加工：文案结构化提取（标题/正文/标签分列）、标签频次与共现分析、选题聚类、元数据导出（Markdown + front-matter → Obsidian / CSV / Notion）。
- **价值**：直接服务"内容创作"这个最终目的，天花板最高。
- **成本**：高。分析类能力若引入 AI 则额外带来模型成本与数据合规审查。
- **风险**：高（范围膨胀、外部模型依赖、AI 引入需过合规）。
- **时机**：**必须等方向 B 的数据地基就位**，否则是无源之水。

#### 方向 D：多平台型 ——「通用素材下载器」

- **内涵**：扩展至抖音 / 微博 / B站 / 公众号等。
- **价值**：覆盖面最广，想象空间最大。
- **风险**：**合规红线高风险**。聚合能力天然会被用作批量抓取工具，与项目"仅限个人非商业备份"的自我约束直接冲突；各平台反爬强度与法务态度差异大，后端将从"单一上游"变成"多上游 fork 维护"，成本陡增。
- **结论**：**本期明确不做**。仅在合规复审明确通过后，作为战略选项重新评估。

### 4.3 方向对比矩阵

| 方向 | 实现成本 | 开发复杂度 | 用户价值增量 | 合规风险 | 与现有定位一致性 | 综合评价 |
|---|---|---|---|---|---|---|
| A 加固型 | 低 | 低 | ★★（修缺陷，无新增维度） | 无 | 完全一致 | **必做前置**，但不可作为方向 |
| **B 资产型** | **中** | **中** | **★★★★★（新增"沉淀+复用"维度）** | **低** | **完全一致** | **★ 推荐主线** |
| C 工作台型 | 高 | 高 | ★★★★★（价值最高） | 中 | 基本一致 | 方向 B 的自然延伸，二期 |
| D 多平台型 | 极高 | 极高 | ★★★★ | **极高** | **冲突** | 本期不做 |

### 4.4 推荐结论与演进路径

**推荐方案：A → B → C 递进，D 搁置。**

```
v1.1 加固   ──►  v1.2 批量   ──►  v2.0 素材库   ──►  v2.x 创作辅助（可选）
(先能稳定用)    (再高效采集)    (再沉淀为资产)     (最后才是加工与增值)
                                  ▲
                          价值分水岭在此
```

**不选其他路线的理由**：

- **不选"直接上方向 C"**：工作台的加工能力建立在"有素材可加工"之上。没有库，加工出来的东西没有归处，用户只会觉得"功能很多但用不上"。
- **不选"跳过 A 直接做 B"**：素材库会让用户**更依赖**这个页面（长会话、大批量操作），而当前页面在断网时是白板、卡住时不可取消。**在脆弱的地基上盖楼，用户流失的代价更大。**
- **不选"直接上方向 D"**：合规风险与维护成本都不符合项目"个人自用 + 开源"的自我约束，且会偏离已验证的同源单上游架构。

**演进路径与触发条件**：

| 阶段 | 进入条件 |
|---|---|
| v1.1 → v1.2 | v1.1 验收通过（内网断外网可用 + 可取消 + 错误分类），且实际使用中确有批量需求 |
| v1.2 → v2.0 | v1.2 批量链路稳定；素材库存储策略与检索入口 2 个关键问题（见第十章）已拍板 |
| v2.0 → v2.x | 库内素材量达到一定规模（建议 ≥200 篇）且出现"需要检索复用/导出"的真实动作 |
| v2.x → 多平台 | 合规复审明确通过，且单平台链路已做到"零维护" |

## 五、目标用户与核心场景

> **假设说明**：以下画像基于项目 README 自述（"部署在我的 NAS 上自用"）与仓库上下文构建，**未做用户调研**，属待确认假设。若与实际不符，第五章至第六章结论需相应调整。

### 5.1 用户角色

| 角色 | 身份 | 核心目标 | 使用频率 | 能力水平 |
|---|---|---|---|---|
| **U1 素材收集者**（主角色） | 内容创作者 / 运营，自托管部署者 | 把看到的好素材（含自己的历史作品）快速、无损地存到本地，并能在需要时找回来 | 追热点期高频（日），平常中频（周） | 熟练（能自建 nginx + Docker） |
| **U2 内容备份者** | 有自己账号历史作品的创作者 | 备份自己发过的图文/视频，防止平台侧丢失或压缩 | 低频（月/季度），但单次批量 | 熟练 |

两个角色都**不需要登录、不需要云同步、不需要协作**——这是本项目相对商业工具的最大差异，也是不能丢的优势。

### 5.2 核心旅程（目标态：四步闭环）

| 步骤 | 用户动作 | 当前支持度 | 目标态 |
|---|---|---|---|
| ① 采集 | 粘贴链接（单条/批量） | 单条 ✅ / 批量 ❌ | 批量粘贴 → 队列解析 → 逐条状态 |
| ② 归档 | 什么都不用做 | ❌ | 解析成功即自动入库（元数据 + 缩略图），无需额外操作 |
| ③ 检索 | 在库内按标题/作者/标签/正文找 | ❌ | 本地全文检索 + 标签云 + 作者聚合 |
| ④ 复用 | 重新下载 / 复制文案 / 导出清单 | ❌（只能重新去小红书找） | 一键重下、批量导出、复制为 Markdown |

**关键设计原则**：②归档必须是**零操作**的。如果入库需要用户额外点击"保存到素材库"，采用率一定很低——用户的心智是"我下载完就完事了"，库化必须做成**副产物**而不是新流程。

### 5.3 关键场景与验收标准

**场景 S1：追热点期批量采集（v1.2 主场景）**

> 作为 U1，我想要一次性粘贴多条分享链接并批量解析下载，以便在追热点时不因逐条操作而错过时效。

- Given 输入框内粘贴了 20 条以换行分隔的小红书分享链接
- When 点击「解析素材」
- Then 系统**逐条**发起解析并各自显示状态（解析中/成功/失败），单条失败不影响其余条目继续解析
- And 全部完成后可「打包下载全部已成功素材」，输出为一个 ZIP（每篇一个文件夹）
- And 单条失败项提供「重试」入口，重试不重新解析已成功的条目

**场景 S2：素材归档与检索（v2.0 主场景）**

> 作为 U1，我想要在库内按关键词/标签/作者找到之前采集过的素材，以便复用而不必重新去小红书翻找。

- Given 素材库中已入库 ≥200 篇素材
- When 在检索框输入关键词（命中标题/正文/作者/标签任一）
- Then **300ms 内**返回结果列表，结果按采集时间倒序，命中片段高亮
- And 支持按标签、按作者筛选，支持「只看图文 / 只看视频」
- And 结果卡片提供「重新下载」「复制文案」「在原站打开」三个动作
- And 素材量大导致首屏渲染时，列表**分页或虚拟滚动**，不出现明显卡顿

**场景 S3：内网断外网仍可用（v1.1 主场景，质量底线）**

> 作为 U1，我在 NAS 内网访问该页面，即使访问端完全没有外网，也应正常渲染与使用。

- Given 访问端浏览器**无法访问任何公网地址**（`cdn.tailwindcss.com` 不可达）
- When 打开 `http://<nginx-host>:1234/`
- Then 页面**完整正常渲染**（样式、图标、布局均正常），不出现无样式白板
- And 解析与下载功能均可用（媒体直链来自 XHS CDN，此时**允许失败**并可重新触发，前提是 U1 临时联通外网）

| 编号 | 需求 | 优先级 | 业务规则 / 验收标准 |

| FR-01 | 样式内联化 | **Must** | 接入 `tailwindcss` + `postcss` 构建链（补 `tailwind.config.js` / `postcss.config.js`，在入口 CSS 中 `@tailwind` 指令），移除 `index.html` 中的 Play CDN 脚本。<br>**验收**：`dist/` 内**不再出现** `cdn.tailwindcss.com`；断外网打开页面样式完整；bundle 内含编译后 CSS（独立 `.css` 产物或内联） |

### 6.3 v1.2 「批量采集」详细设计

|---|---|---|---|

### 6.4 v2.0 「素材库」详细设计（价值分水岭）

| 编号 | 需求 | 优先级 | 业务规则 / 验收标准 |
|---|---|---|---|
| FR-15 | 存储升级至 IndexedDB | **Must** | 素材元数据 + 缩略图迁至 IndexedDB（替代 localStorage 的 50 条 / 5MB 上限）；封装统一存储层 `utils/vault.ts`，含版本号与迁移逻辑。<br>**验收**：≥500 篇素材可正常读写；升级时 localStorage 既有历史自动迁移 |
| FR-16 | 自动入库（零操作） | **Must** | 每次解析成功即自动写入素材库，**无需用户额外点击**；同一作品ID 重复采集时按「更新」处理。<br>**验收**：解析 1 篇成功后刷新页面 → 素材库中已有该条 |
| FR-17 | 素材卡片墙 | **Must** | 素材以卡片墙呈现：封面缩略图、标题、作者、标签、类型（图文/视频）、采集时间；支持分页或虚拟滚动。<br>**验收**：500 条下列表滚动流畅，无明显掉帧 |
| FR-18 | 本地检索 | **Must** | 支持按标题 / 正文 / 作者 / 标签关键词检索，结果倒序 + 命中高亮；支持标签、作者、类型筛选。<br>**验收**：500 条数据下检索响应 <300ms |
| FR-19 | 软删除与回收站 | **Must** | 删除为软删除（标记 deleted），进入回收站，支持恢复；回收站支持手动清空。<br>**验收**：误删后可在回收站恢复；清空回收站需二次确认 |
| FR-20 | 存储配额守卫 | Should | 监听 `navigator.storage.estimate()`；用量超阈值（建议 80%，估算值）时提示并提供处置：清理回收站 / 仅保留元数据（丢弃缩略图）/ 导出后清库。**两档存储策略**：默认存元数据 + 缩略图；可选"仅元数据（不含缩略图）"以省空间。<br>**验收**：模拟配额不足时给出明确可执行的处置路径，而非静默失败 |
| FR-21 | 增量更新提示 | Should | 重复采集同一作品时，若元数据有变化（点赞/评论数、标题、描述），提示"该素材有更新"，提供保留/覆盖选择。<br>**验收**：同一链接二次采集 → 出现更新提示，不静默覆盖 |
| FR-22 | 导出素材清单 | Should | 导出为 JSON 与 CSV（含全部元数据字段），支持按当前筛选结果导出；提供「重新下载选中项」。<br>**验收**：导出文件可被本产品重新导入并还原（至少元数据可还原） |
| FR-23 | 标签与作者聚合视图 | Could | 按标签生成标签列表（含计数），按作者聚合其全部素材。<br>**验收**：点击某标签 → 显示该标签下全部素材 |
| FR-24 | 数据备份与恢复 | Could | 一键导出完整库（含缩略图）为单文件；支持从该文件恢复，覆盖前二次确认。<br>**验收**：浏览器存储被驱逐后可用备份文件恢复 |

**v2.0 关键设计决策（开工前必须拍板，见第十章待确认问题）**

1. **存元数据还是存媒体本体**——决定存储成本与"离线可看"能力，是本版最大分叉。
2. **检索是否需要跨设备/跨浏览器**——决定是否需要引入服务端存储，进而显著改变隐私面与复杂度。
3. **索引字段设计**——建议为 `作品ID`（去重键）、`采集时间`、`作者ID`、`标签数组` 建立索引；`作品ID` 唯一约束。

## 九、明确不做清单

> 范围蔓延是产品最大的风险。以下条目**本期不做**，如需变更须走需求变更评估（影响范围 / 工期 / 成本 / 风险 / 干系人一致性五要素），评估通过才进入排期。

### 9.1 合规性「不做」（硬约束，不接受排期压缩）

| 不做项 | 原因 |
|---|---|
| 自动化登录 / Cookie 托管 / 账号级抓取 | 突破"个人非商业备份"定位 |
| 定时任务 / 批量链接文件导入 / 无限量抓取 | 语义上即为批量抓取工具 |
| 绕过平台风控（代理池轮换、验证码破解、指纹伪装） | 违规 |
| 去除/伪造平台版权标识、二次分发 | 侵权 |
| 多平台聚合抓取（抖音/微博/B站等） | RK-04；需独立合规复审 |
| 引入任何会把素材内容外传的第三方服务（含用于训练的 AI 接口） | 隐私与合规 |

### 9.2 架构性「不做」（沿用既有决策，避免反复讨论）

| 不做项 | 依据 |
|---|---|
| 引入 Redux / RTK Query 等状态库 | `activeContext.md` 决策 3 |
| fork 后端、或对后端做本地手改（cp hack） | 决策 5；唯一路径是 `git pull` + `docker compose build` |
| 改动 5556 端口绑定收敛（如改成 `192.168.2.3:5556`） | 决策 7；会同时废掉 nginx upstream backup 与 openp2p/tailscale 直连 |
| 改变「同源反代」架构、把后端地址做成前端可配置项 | 决策 1 / 2 |
| 引入服务端用户体系 / 权限模型（在明确跨设备需求之前） | 见第十章待确认问题 2 |

### 9.3 阶段性「暂不做」

| 不做项 | 何时可做 |
|---|---|
| AI 摘要 / 聚类 / 选题推荐 | FR-29 三项前置评估（合规/成本/行为边界）全部通过后 |
| 跨设备 / 跨浏览器同步 | 明确确有需求，且接受引入服务端存储带来的复杂度与隐私面变化 |
| 素材图片的本地编辑 / 裁剪 / 加字 | 完全超出"采集与归档"的产品边界 |
| 发布/回传小红书等平台 | 违规 |

## 十、关键假设与待确认问题

### 10.1 本方案所依赖的关键假设（如不成立请推翻）

| 编号 | 假设 | 若假设不成立的后果 |
|---|---|---|
| A-01 | 产品定位保持**个人自用 + 开源**，不做商业化 | 若商业化，第四~六章全部需重做（合规、多用户、存储与服务端架构均变） |
| A-02 | 后端保持 XHS-Downloader，且通过 nginx 同源调用 | 若换后端，`types.ts` 契约与错误分类逻辑（FR-03）需重写 |
| A-03 | 目标浏览器为现代浏览器（最近两个大版本） | 若需兼容老旧浏览器，IndexedDB/虚拟滚动/`navigator.storage` 均需降级方案 |
| A-04 | 主要使用场景为桌面端，移动端为次要 | 移动端优先级需上调至与批量同级 |
| A-05 | 单次批量规模在"几十条"量级，非"几千条" | 若为后者，需重新设计队列持久化与断点续传，v1.2 复杂度翻倍 |
| A-06 | 用户能接受素材数据仅存于本地浏览器（无云备份） | 若不接受，v2.0 需引入服务端存储，架构与隐私面显著变化 |

### 10.2 待确认问题（决定 v2.0 走向，建议在 v1.2 结束前拍板）

| 编号 | 问题 | 选项与影响 |
|---|---|---|
| **Q1** | **素材库存什么？** 只存元数据 + 缩略图，还是连媒体本体一起存？ | **只存元数据**：轻（单条约 1-5KB，估算）、安全、复用需重新下载。<br>**存媒体本体**：可离线查看、真备份，但单篇可能几十 MB，需 File System Access API 或 OPFS，配额压力大。<br>**建议**：默认「元数据 + 缩略图」，媒体本体走"可选落盘到本地目录"（需浏览器支持 OPFS / File System Access）。 |
| **Q2** | **是否需要跨设备 / 跨浏览器访问素材库？** | **不需要**（推荐）：保持纯前端，零服务端，隐私面最小。<br>**需要**：必须引入服务端存储与鉴权，复杂度与隐私面显著上升，需重新做架构设计。<br>**建议**：先不做；用 FR-22/FR-24 的"导出/导入单文件"作为跨设备迁移的替代方案。 |
| **Q3** | **主用户是否只有你本人（纯自用）？** | 若纯自用：v2.0 可**跳过一切用户体系与权限设计**，把全部力气放在检索、导出与性能上。<br>若有他人使用：需补多用户隔离与访问控制评估。<br>**建议**：按纯自用处理（与 README 自述一致）。 |
